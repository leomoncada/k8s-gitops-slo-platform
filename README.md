# k8s-gitops-slo-platform

[![ci](https://github.com/leomoncada/k8s-gitops-slo-platform/actions/workflows/ci.yml/badge.svg)](https://github.com/leomoncada/k8s-gitops-slo-platform/actions/workflows/ci.yml)
[![incidents](https://github.com/leomoncada/k8s-gitops-slo-platform/actions/workflows/incidents.yml/badge.svg)](https://github.com/leomoncada/k8s-gitops-slo-platform/actions/workflows/incidents.yml)

**Installing Prometheus is not SRE. Proving that a specific failure produces a
specific alert, within a measured time, and that the runbook recovers it, is.**

A Kubernetes platform that runs on a laptop at zero cost, delivered with GitOps
(Argo CD), observed with SLOs (Sloth, Prometheus, Loki, Tempo, OpenTelemetry),
and exercised by six reproducible incidents that CI runs on a fresh cluster
every night.

## What this proves

- **Incidents are tests.** Six failures, each with an injection, an expected
  alert, a recovery check and a runbook. CI runs them in parallel and publishes
  time to detect and time to recover.
- **GitOps is exercised, not just installed.** A bad release and a memory leak
  arrive as real commits; the fix is a real `git revert`. Manual drift is
  undone by Argo CD self-heal in seconds.
- **SLOs drive the alerts.** Multiwindow, multi-burn-rate alerts generated by
  Sloth catch a release that every health check let through.
- **Alert logic is unit-tested.** promtool tests every rule with synthetic
  series, including both the real 30-day windows and the compressed CI windows.
- **It runs anywhere Docker runs.** `make up` builds the whole platform in kind
  in about four minutes, with no cloud account and no credentials.

## The incidents

| # | Incident | Injection | Caught by | Detect | Recover |
|---|---|---|---|---|---|
| 1 | [Bad release](incidents/01-bad-release/README.md) | Commit of orders 1.1.0, a serializer bug | `OrdersAvailabilityBurnRate` page, after every health check passed | 25 s | 76 s |
| 2 | [Slow Postgres](incidents/02-slow-dependency/README.md) | Chaos Mesh: +400 ms on all Postgres egress | `OrdersLatencyBurnRate` page, then a trace shows the slow query | 15 s | 80 s |
| 3 | [Memory leak](incidents/03-memory-leak/README.md) | Commit of orders 1.2.0, a cache that never evicts | `OrdersContainerOOMKilled`, a real OOM of the app | 225 s | 16 s |
| 4 | [Manual drift](incidents/04-manual-drift/README.md) | `kubectl set env` and a deleted PodDisruptionBudget | Argo CD self-heal restores both, nobody is paged | healed in 2 s | |
| 5 | [Node failure](incidents/05-node-failure/README.md) | `docker stop` on a worker | `KubeNodeDown`; replicas move to the surviving worker | 70 s | 5 s |
| 6 | [Traffic spike](incidents/06-traffic-spike/README.md) | k6 ramping to ~350 req/s | `OrdersHPAMaxedOut` once autoscaling has no headroom | 86 s | 61 s |

Detect: from the injection to the alert firing. Recover: from the alert to the
SLI back within objective (or, for non-SLO alerts, to the alert resolving).
Measured by [this CI run](https://github.com/leomoncada/k8s-gitops-slo-platform/actions/runs/37136686289)
on 2026-10-03 (compressed windows, one fresh cluster per incident); the
[incidents workflow](https://github.com/leomoncada/k8s-gitops-slo-platform/actions/workflows/incidents.yml)
publishes fresh numbers on every run. Postmortems:
[#1](docs/postmortems/2026-10-03-bad-release-1.1.0.md),
[#2](docs/postmortems/2026-10-03-slow-postgres.md).

## Architecture

```
                ┌──────────────── kind cluster (local or CI) ──────────────────┐
  make up ──►   │  infra node (control-plane)                                  │
  (seeds the    │   git-server ◄── Argo CD (app-of-apps) ──► installs all:     │
   working      │   Prometheus · Alertmanager · Grafana · Loki · Tempo         │
   tree)        │   Postgres · k6 baseline traffic · alert sink                │
                │                                                              │
                │  worker 1, worker 2                                          │
                │   orders replicas only (+ OTel Collector, chaos daemon)      │
                │                                                              │
                │  incident test: inject ─► alert in Alertmanager ─► verify    │
                │  (fault or commit)        detection and recovery             │
                └──────────────────────────────────────────────────────────────┘
```

- **Argo CD reads from a Git server inside the cluster** (Soft Serve), seeded
  from your working tree by `make up` and updated by `make sync`. Local changes
  apply without pushing anywhere, and incidents commit and revert without
  tokens ([ADR 1](docs/adr/0001-in-cluster-git-server.md)).
- **Every platform component runs on an infra node**, so a worker failure only
  ever hits the application ([ADR 9](docs/adr/0009-single-postgres-on-infra-node.md)).
- **orders** is a small FastAPI service with Postgres, Prometheus metrics,
  OpenTelemetry traces and JSON logs carrying the trace id. It has three
  releases: a correct one, one with a serializer bug, and one with a memory leak.

## Quickstart

Requirements: Docker, [kind](https://kind.sigs.k8s.io), kubectl, helm, Python 3.14.

```bash
make doctor     # checks the tools
make up         # whole platform in kind, about 4 minutes
make demo       # incident #1, narrated
make incidents  # all six
make down
```

| Service | URL |
|---|---|
| Grafana | http://localhost:30300 (anonymous viewer, `admin`/`admin`) |
| Prometheus | http://localhost:30090 |
| Alertmanager | http://localhost:30093 |
| Argo CD | http://localhost:30080 (anonymous read-only) |
| orders API | http://localhost:30800 |

Ports are bound to `127.0.0.1` only. Dashboards: `orders: service` and
`orders: SLOs`.

## What building it taught

Found while making the incidents pass, each one now a test, an ADR or a line
in [DESIGN.md section 17](docs/DESIGN.md#17-changes-during-implementation):

- **Server-side SLIs have a blind spot.** When a node died, k6 sent 990
  requests and 2.0% of them failed. The server counted only 923 requests and
  zero errors: requests to pods on the dead node never reach a server to be
  counted. k6 pushes client-side metrics to Prometheus to measure what the SLO
  cannot.
- **A slow dependency becomes errors.** 400 ms on Postgres exhausted the
  connection pool, and 19% of reads failed with 503 during the delay
  ([postmortem](docs/postmortems/2026-10-03-slow-postgres.md)).
- **A sync hook can block the fix.** An Argo CD hook waits for earlier waves to
  be healthy, so an OOM-looping release would have blocked its own
  `git revert`. The schema moved to an idempotent init container
  ([ADR 8](docs/adr/0008-memory-incident-real-leaking-release.md)).
- **Targeted chaos misses Service traffic.** Chaos Mesh delays aimed at a
  target pod do not apply to traffic sent to a ClusterIP, verified on macOS and
  on GitHub's Ubuntu 24.04 and 26.04 runners
  ([ADR 7](docs/adr/0007-chaos-mesh-delay-on-postgres-egress.md)).
- **Observers must not share the failure domain.** Prometheus and the load
  generator first landed on workers, where the node-failure incident would have
  blinded them; everything but the app now runs on an infra node
  ([ADR 9](docs/adr/0009-single-postgres-on-infra-node.md)).
- **"No data" is not zero.** With no 5xx at all, the availability SLI returned
  no data instead of 0, exactly when the service was healthiest
  (`or vector(0)` in [slos/orders.yaml](slos/orders.yaml)).

## CI

| Workflow | Trigger | What it proves |
|---|---|---|
| [`ci.yml`](.github/workflows/ci.yml) | every push and pull request | Lint (ruff, shellcheck, helm, kubeconform against Kubernetes and CRD schemas), generated SLO rules not hand-edited, promtool tests for every alert, orders tests against a real Postgres, and the whole platform from scratch in kind with a clean alert baseline |
| [`incidents.yml`](.github/workflows/incidents.yml) | push to `main`, nightly, manual | All six incidents in parallel, each on a fresh kind cluster, with time to detect and time to recover in the run summary |

**Compressed windows in CI.** Real SLO windows (5 minutes and 1 hour for the
fast page) would make each incident test take an hour. The CI overlay shrinks
the SLO period to 1 hour and the windows with it, but keeps every burn-rate
threshold of the real windows (14.4, 6, 3, 1). Same math, minutes instead of
hours ([ADR 6](docs/adr/0006-compressed-slo-windows-in-ci.md)). Locally,
`make up` uses the real 30-day windows; `OVERLAYS="kind ci" make up` switches
to the CI ones.

## Known limits

- **kind is not production.** One machine, no real network between nodes, no
  cloud load balancer. Phase 2 runs the same manifests on EKS.
- **Postgres is a single instance**, pinned to the infra node: a known single
  point of failure ([ADR 9](docs/adr/0009-single-postgres-on-infra-node.md)).
- **Local Prometheus keeps 12 hours of data**, so the 1-day and 3-day windows
  and the 30-day budget only see what the cluster has lived through.
- **Credentials are local-only defaults** (Grafana `admin`/`admin`, a
  plaintext Postgres password in a Secret). Nothing is exposed beyond
  `127.0.0.1`.

